# Forge run log — 20-search

## Codebase Patterns

- **Engine package, plugin shell.** Testable logic (schema, migrations, query parsing) lives in a
  `packages/*` engine with a `test` script; the `plugins/*` package owns only lifecycle, UI and
  settings. `@arxhub/sql` + `plugins/search` follow `@arxhub/sync` + `plugins/sync`.
- **A browser-and-Node package uses `createNodeConfig`** in its `vite.config.ts` (like `@arxhub/vfs`):
  the browser bundle imports the package from `src/`, so the package's own vite config never touches
  the app build, and `createBrowserConfig` has no `lib` entry.
- **A plugin's public surface is `src/ui.ts`** (`exports: { "./ui": "./src/ui.ts" }`), re-exports only;
  instances import `@arxhub/plugin-<name>/ui`.
- **Instance registration is per instance**: `instances/{dev,client,app}/src/main.ts` each list plugins
  themselves and each `package.json` must name the workspace dep. `instances/server` is a separate
  decision every time — a client-only plugin does not go there.
- **PGlite needs `optimizeDeps: { exclude: ['@electric-sql/pglite'] }`** in an instance's vite config:
  it resolves its `.wasm` / `.tar.gz` payload with `new URL(...)`, which esbuild's pre-bundling breaks.
- **An engine package never imports vue.** Observable state in `packages/*` is a snapshot getter plus
  `subscribe(listener): () => void`; the plugin subscribes once and mirrors it into `ref`s. The engine
  stays testable under plain vitest and the reactivity stays in the layer that renders.
- **PGlite returns `bigint` columns as strings** (`size`, `mtime`). Cast in the query — `size::float8 AS
  size` — rather than coercing in TS: ms timestamps and file sizes are far inside what a double holds
  exactly, and a `Number(row.size)` sprinkled at each call site is the bug that comes back.
- **`type`-only imports are free across the layer line.** `packages/sql` takes `import type { Logger }
  from '@arxhub/logger'` — erased at build, so pino never reaches the browser through it.
- **`pnpm --filter <pkg> build` is broken repo-wide for `createNodeConfig` packages** (`@arxhub/sync`,
  `@arxhub/sql`): `rollup-plugin-node-externals@9` throws `undefined is not a function` under vite 8's
  rolldown. Pre-existing and unrelated to any feature here — verify a package with `tsc --noEmit` +
  `vitest`, and verify the bundle through an instance build (which imports workspace `src/`).

- **Learnings for future iterations:**
  - **`statement_timeout` does not work in PGlite 0.5.4.** It is applied and readable
    (`current_setting` returns the requested value) but never fires: Postgres arms it with
    `setitimer`/`SIGALRM` and the WASM build receives no signals. A JS-side deadline is no help
    either — the query holds the single thread, so no timer callback runs until it finishes (verified:
    a 200 ms `setTimeout` racing `pg_sleep(2)` never fired). The only real containment would be
    running PGlite in a worker and terminating it, which is a different architecture. The engine sets
    the limit anyway so it starts working the day PGlite delivers the interrupt; `durationMs` is what
    reports the cost today. The QA doc's check 9 and acceptance criterion 5 cannot pass as written.
  - **A failed statement must be followed by `ROLLBACK`** or the next query dies with 25P02. Verified.
    `SET TRANSACTION READ ONLY` genuinely refuses DELETE/UPDATE/DDL with 25006.
  - **`SET` takes no bind parameters**, so the timeout goes through
    `SELECT set_config('statement_timeout', $1, true)` — nothing is pasted into SQL text.
  - **PGlite gives only the column OID**, not a type name. The index reads `pg_type` once at open and
    resolves names from that map; resolving lazily would mean a query inside the READ ONLY
    transaction needing a query of its own.
  - **A cold PGlite costs ~1 s.** Tests share one index per file and clean the tables between cases;
    a per-test `openSqlIndex` makes the suite minutes long. `dataDir: 'memory://'` for tests.
  - **`start()` awaits the open**, which adds roughly a second of boot before first paint. That is the
    literal reading of the spec (and what makes `status = 'failed'` observable right after boot), but
    APP-01-05 should revisit it if boot feels slow — the `opening` status only earns its keep once
    something renders it.
  - `migrate` also clears the non-version `index_meta` rows when it discards the content tables: a
    `scan_cursor` left from a dropped index would make the next walk resume past documents that are
    no longer there. APP-01-02 owns the cursor and can rely on that.
  - The engine's `readOnly` reports a rejected query as a **value** (`{ ok: false, message, code,
    position, durationMs }`), never a throw; `query` throws. `SearchExtension` keeps that split:
    `query` throws `searchIndexUnavailable()` when there is no index (an empty result would read as
    "nothing matches"), `readOnly` returns a failure with code `index_unavailable`.
  - Not verified in a real browser yet (no e2e run in this task): that `idb://arxhub-sql` opens under
    Chromium. The client build emits every PGlite asset, and PGlite needs no COOP/COEP (it is
    single-threaded), so this is expected to work — but it is the one claim resting on the build
    rather than on a run.

## 2026-07-26 - APP-01-02

- Taught the engine to read a file and taught the walk to keep the index level with the store.
  - `parseDocument(pathname, bytes, stat?)` is pure — bytes in, rows out — so every parsing rule is a
    unit test rather than a database round trip. Kind from the extension (`.md`/`.markdown` markdown,
    `.arx` arx, `.txt`/`.text`/no extension text, everything else binary); title from the metadata,
    else the first heading, else the file name, and never empty; `title_fold`/`name_fold` lower-cased
    with the diacritics folded (NFD, drop `\p{M}`) so they match Postgres' `unaccent`.
  - Markdown is read line by line rather than with a markdown library: the index needs the text a
    reader sees and its rough shape, and a parser dependency would have to run in the browser too.
    Blocks are `heading` (with `level`), `paragraph`, `list-item` (one per item), `code`, `quote`;
    markup is stripped everywhere except in `code`. `.arx` is walked as the tree it is, opening the
    containers (`bullet_list` → one `list-item` per item) and reading `link` marks as refs; a file that
    is not a readable tree comes back as `text` with one paragraph, so it is still findable by name.
  - Tags are read from the *stripped* text (a URL fragment `](page#section)` is then not a tag) and refs
    from the *raw* text (a link is only a link while its brackets are there) — never from a `code` block.
    A link with a URL scheme, a `//` host or a bare `#anchor` is not an intra-vault ref.
  - `indexDocument` is one transaction per document: upsert the row, delete its blocks/tags/refs, insert
    the new ones. `ref.target_path` is resolved against `document` — next to the source first, then from
    the root, each with and without a document extension — and a target that is not indexed stays null.
  - `createIndexer(index, vfs, options).scan()` resumes from `index_meta.scan_cursor`, skips a file whose
    `size` and `mtime` match its row, falls back to the content hash (a touched file that says the same
    thing only gets its stat fields updated), sweeps rows whose file is gone, checkpoints the cursor and
    yields every `batchSize` documents, and joins rather than duplicates a walk already running.
  - `plugins/search`: `start()` fires `indexer.scan()` **without awaiting it** (FR-223) and `stop()`
    cancels then awaits `indexer.running` before closing the index. `SearchExtension` gained `indexer`,
    `processed` and `reindex()`; `status` reads `scanning` while the walk runs.

- **Learnings for future iterations:**
  - **The sweep cannot be "delete everything the walk did not see."** A resumed walk only sees the tail
    of the store, so that rule would empty the index on the first interrupted boot. It is `exists()` on
    the rows the walk did not visit instead — bounded, because on a complete walk that set is exactly
    the stale rows.
  - **A cursor checkpoint reprocesses at most `batchSize` files.** `walker.cursor()` is the state *after*
    the file it just returned, so resuming skips what was already written; the files handled since the
    last checkpoint are simply done again, which is idempotent.
  - **`reindex()` cannot just join a running scan** (it must actually rebuild) and cannot ignore it
    (the walk holds transactions over tables it is about to empty). It cancels, awaits, clears, then
    scans — and `runScan()` resets the cancel flag so the stop does not carry into the new walk.
  - **A same-size, same-mtime write is real** — two writes inside one millisecond, or an edit that
    replaced text with text of the same length. `indexPath()` therefore forces a re-read and only the
    walk takes the stat shortcut; a test proves it by rewriting `# Первое` as `# Второе` (same bytes
    long) with the timestamp pinned.
  - **A parse failure is injected with a `ScopedFileSystem` subclass whose `read()` throws**, over the
    real `NodeFileSystem`. `chmod 000` was rejected — it does nothing when the suite runs as root.
  - **`.arxmeta` is already filtered by the Node and Tauri backends' `list()`**, so a walk test cannot
    observe the engine's own skip. That rule is covered by a unit test on `isIndexablePath` instead; the
    engine keeps the check because the HTTP and in-memory backends make no such promise.
  - **No YAML dependency was added.** Frontmatter is read by a small subset parser (`key: scalar`,
    `key: [a, b]`, a block sequence) because the index reads `title` and `tags` and hands the rest to
    `jsonb`; a shape it does not understand comes back as the raw string rather than being lost. If a
    later feature needs real YAML, that is a catalog entry and a decision, not a quiet import.
  - **A forward ref stays `target_path = null`.** Resolution happens when the *source* is written, so a
    link to a note the walk indexes later is only resolved the next time the source is reindexed. The
    spec asks for exactly this (BE 3.4) and nothing more, but APP-01-04 must not read the `ref` table as
    a complete backlink graph — resolve at query time, or accept the staleness knowingly.
  - **`exclude`, `maxFileSize` and `batchSize` are still defaults, not config.** The engine exports
    `DEFAULT_MAX_FILE_SIZE` (2 MiB) and `DEFAULT_BATCH_SIZE` (32) and the plugin passes neither.
    APP-01-06 owns the settings section and should route them through the plugin's config schema —
    tunables do not belong in module constants once there is a page to put them on.

- **Learnings for future iterations:**
  - **There was no VFS contract suite to reuse.** `packages/vfs/src/__tests__/interface.test.ts` is
    cursor serialization only, and two test files each carried their own throwaway `MemoryFileSystem`.
    So acceptance criterion 9 is now a real one: `vfs-contract.ts` exports
    `describeFileSystemContract(label, create)` — 14 checks covering read/write, streams, list/walk,
    `file()` helpers, the hash sidecar, delete-with-force, `lock`/`acquireLock`, `appendEntry` and
    `renameEntry` — and `observed-file-system.test.ts` runs it three times: bare backend, decorator over
    it, decorator over a rename-capable backend. A decorator that changes any of them fails there.
    The two older duplicate fakes were left alone (out of scope); a later task can fold them in.
  - **`ObservedFileSystem.wrap()`, not `new ObservedFileSystem()`.** `isRenameCapable()` asks by looking
    for the method, so a decorator that always has `rename` claims a capability its backend may not
    have. `wrap()` returns a private rename-capable subclass only over a backend that renames natively.
    In production this means the vault view is **not** rename-capable — `ScopedFileSystem` has no
    `rename` — so the explorer's rename is `renameEntry`'s copy + delete *through* the decorator, and
    arrives as `written`(new) + `deleted`(old). Both shapes are covered by tests.
  - **The decorator wraps the OUTSIDE of the scope**, so subscribers get vault-relative paths
    (`notes/a.md`, not `vault/notes/a.md`) — the same coordinates `document.path` stores. That is not
    incidental: swapping the order would silently index every path with a `vault/` prefix.
  - **A listener runs synchronously inside the operation that notified it**, usually while that path's
    lock is still held (`VirtualFileImpl.write` notifies from inside `vfs.lock`). It may only record and
    return; anything slower deadlocks or stalls the writer. `VfsWatcher` also catches a listener that
    throws (reporting it through `onError`, which `VfsPlugin` routes to its logger) — a broken subscriber
    must never fail a write that already succeeded.
  - **`plugins/search` had no test setup**; it now has `"test": "vitest"` and two suites.
    `vault-freshness.test.ts` composes the real production stack minus the database — `NodeFileSystem` +
    `ScopedFileSystem('vault')` + `ObservedFileSystem` + the real queue over a fake `Indexer` — which is
    what catches wiring mistakes (paths, sidecars, lock re-entrancy) without importing `@arxhub/sql` at
    runtime. Deliberate: the engine was being edited concurrently, and the queue's contract with it is
    only `indexPath` / `removePath`.
  - **`@arxhub/logger` is now a peer dep of `plugins/search`** (`import type { Logger }` in the queue) and
    `@arxhub/vfs-node` a dev dep (the freshness suite). The vite `external` list had to grow to match.
  - **`debounceMs` is a plugin arg** (`SearchPluginArgs.debounceMs`, default `DEFAULT_DEBOUNCE_MS = 400`),
    not config yet — the same debt as `exclude`/`maxFileSize`/`batchSize`. APP-01-06 owns the settings
    section and should route all four through the config schema.
  - **A directory rename or delete leaves stale rows.** One change is reported on the directory path, and
    `removePath()` on a directory removes no document rows, so the documents under it survive in the
    index until the next full scan. Handling it properly needs a delete-by-prefix in the engine
    (`packages/sql`), which was another worker's file during this task — recorded rather than guessed at.
  - **For APP-01-05:** the freshness path is invisible in `SearchExtension.status` on purpose. `status`
    reads `scanning` only while `indexer.scan()` runs; a debounced single-path reindex leaves it `ready`,
    because a flicker to `scanning` on every keystroke would be noise and would disable the search box.
    What *does* move is `documentCount` (the queue refreshes it through the indexer's own status
    snapshot), so a new note appears in the count without any status change. If the UI wants "saving…"
    feedback it needs a signal of its own, not a reading of `status`.

## 2026-07-26 - APP-01-04

- Taught the engine to read a search string and to answer it. All of it in `packages/sql`; no plugin,
  instance or VFS file touched (APP-01-03 owned those in the same tree).
  - `search-query.ts`: `parseSearchQuery(input)` splits the string into lexemes — a quoted run may hold
    whitespace, which is what makes both `"two words"` and `title:"two words"` one lexeme — and sorts
    them into `clauses` (each has to match; one term = a word or phrase, several terms = an `OR` group),
    `exclusions`, `qualifiers`, `freeText` (the input minus the qualifier spans) and `prefixLast`. Never
    throws: an unclosed quote becomes a phrase to end of string, a valueless qualifier and a dangling
    `OR` are dropped with a `warnings` entry, and an empty query comes back `empty: true`.
  - `buildTsQuery(parsed, { fold })` folds every word to letters/digits/underscore, so the assembled
    expression cannot contain a tsquery operator the user wrote and string concatenation is safe there.
    Words join with `&`, a phrase with `<->`, an exclusion with `!` (parenthesised when it is a phrase),
    an `OR` group with `|` in parentheses, and the last word of the last clause takes `:*` when
    `prefixLast`.
  - `search.ts`: `searchDocuments(index, parsed, options)` — qualifier filters, the three match modes,
    `scope`, `sort`, `limit`+1 probing for `hasMore`, a separate count, and one follow-up query for
    block snippets through `ts_headline`. Every user value is a bind parameter; a `Params` collector
    hands out `$n` so the two queries that share a WHERE clause can each build their own numbering.
  - `snippet.ts`: `SNIPPET_MATCH_START`/`END` are U+0002/U+0003 and `snippetSegments(text)` splits a
    snippet into `{ text, match }` — the UI renders segments as text and never inserts document content
    as markup (FR-233).
  - `errors.ts`: `searchRegexInvalid(pattern, cause)` → `SearchRegexInvalidError` (400).

- **Learnings for future iterations:**
  - **The `'simple'` configuration does not unaccent**, and `document.tsv` stores the title as written,
    so full-text matching is case-insensitive but *not* diacritic-insensitive. Searching `cafe` finds a
    note titled `Café` only through the fuzzy title branch (`similarity(title_fold, freeText)`), which is
    why that branch is kept in the `titles` scope too. For the `titles` scope the full-text side matches
    `to_tsvector(title_fold)` against `buildTsQuery(parsed, { fold: true })` — the folded query against
    the folded column — so narrowing to titles does not silently lose the diacritic case.
  - **A `!` inside the tsquery is not enough to exclude.** A document found through
    `similarity(title_fold, …)`, or through a qualifier alone, never touches the tsquery, so `-word`
    is a top-level `NOT (d.tsv @@ …)` as well. Under `caseSensitive` it is a `strpos` exclusion instead,
    to match the matcher the positive side uses.
  - **`similarity(title_fold, $1) >= $2` is a sequential scan and that is fine here**: 5000 documents
    cost 16 ms. The index-assisted alternative is the `%` operator, but `%` reads its threshold from
    `pg_trgm.similarity_threshold` rather than from a parameter, so honouring `fuzzyThreshold` would
    mean a `set_config` round trip per search. Verified both plans with EXPLAIN; both seq-scan the OR.
    Revisit only if the base grows an order of magnitude.
  - **`ts_headline` takes its option string as a bind parameter**, and raw control characters survive it
    unquoted — `StartSel=<U+0002>, StopSel=<U+0003>` works. `MaxFragments=0` gives one window per block,
    which is what a block is for. `MinWords` must be strictly less than `MaxWords` or Postgres refuses.
  - **`ts_headline` with a query that does not match returns the first `MinWords` words, not `MaxWords`.**
    The "found by title" fallback therefore does not use it at all: it reads `block.content` of the
    opening block (`DISTINCT ON (doc_path) … ORDER BY doc_path, ordinal`) and cuts it to `snippetWords`
    in TypeScript, so an unhighlighted snippet is guaranteed to carry no marks.
  - **A title taken from the first heading is also a block**, so a document "found only by its title"
    normally still has a matching block. The fallback path is only reachable when the title came from
    frontmatter (or from the file name) — which is what the test for it uses.
  - **`to_tsquery('simple', '')` is a notice, not an error**, and yields an empty tsquery that matches
    nothing. The searcher still skips the branch when the built expression is empty, so a query of
    qualifiers only never asks the DBMS for a match at all.
  - **`= ANY($n::text[])` takes a JavaScript array straight through PGlite**; no per-path placeholder
    list is needed for the snippet queries.
  - `strpos(column, $n) > 0`, not `LIKE '%' || $n || '%'`: a qualifier value holding `%` or `_` is a
    value, not a wildcard. There is a test that `title:%` finds nothing and that
    `title:"'; DROP TABLE document; --"` leaves the three seeded rows in place.
  - **`limit`, `offset`, `snippetsPerDocument`, `snippetWords` and `fuzzyThreshold` are exported
    defaults** (`DEFAULT_SEARCH_LIMIT` = 50, `DEFAULT_SNIPPETS_PER_DOCUMENT` = 3,
    `DEFAULT_SNIPPET_WORDS` = 24, `DEFAULT_FUZZY_THRESHOLD` = 0.3). APP-01-06 owns the settings section
    and should route them through the plugin's config schema.
  - **APP-01-05 calls `parseSearchQuery` then `searchDocuments`** — the engine deliberately has no

## 2026-07-26 - APP-01-06 (fix: boot-blocking start)

- Regression from the full e2e run (95 passed / 1 failed): `mobile.spec.ts` died in the shared `app`
  fixture on `expect(page.getByRole('main')).toBeVisible()` at 5 s, only under parallel load. Cause was
  `SearchPlugin.start()` awaiting the config read and then `openSqlIndex` — `ArxHub.start()` awaits every
  plugin's `start()`, so nothing painted until PGlite had fetched and booted its WASM.
- **The rule, and it is reusable: a plugin's `start()` must not hold the first paint.** Written up in the
  root `AGENTS.md` next to "Boot recovery", because it is a property of the lifecycle rather than of search.
  A slow bring-up sets a pending status, runs **detached**, and everything that needs the resource awaits a
  readiness promise instead of assuming it is there.
  - `SearchPlugin.start()` now sets `status = 'opening'` and returns; `bringUpIndex()` does the config read →
    `openSqlIndex` → `readIndexState` → indexer + queue + settings watch → background `scan()`. The config
    read stayed first inside it, because `exclude`/`maxFileSize` decide what the very first walk covers.
  - `start()` is **deliberately not `async`**: its whole body runs in the caller's tick, so a `stop()` in the
    same tick always finds `bringUp` assigned. With `await super.start(ctx)` first the two interleave — and
    worse, the resumed `start()` reset `stopping` back to false after the stop had set it, so the bring-up
    went on to open an index nothing was left to close. Verified: restoring the `async` form crashes the
    vitest worker with a leaked PGlite instance.
  - `stop()` sets `stopping`, then **awaits the bring-up** before tearing anything down; `bringUpIndex()`
    re-checks `stopping` after every await and closes the index itself if the stop landed mid-open.
  - `SearchExtension.search` and `reindex` join `query`/`readOnly` in awaiting readiness, so a word typed one
    second into the boot is answered rather than told the index is not open. `schema` needs no gate — it is a
    constant of the engine, right before the index opens and after one has failed to.
  - `useIndexStatus` gained an `opening` state ("Opening the index…", pulsing dot, Reindex inert). Without it
    the rail read "0 in index" during the bring-up, which is a claim about the vault rather than about a
    database that has not answered yet.

    `LazyContainer<object>` with `VaultVfs`/`VaultWatcher` bound + an `EventEmitter<EventMap>` is a usable
    `PluginContext`; `create()` and then setting `search.config` by hand stands in for `configure()`, which
    would otherwise drag in the shell, panels and settings extensions the test says nothing about.
  - **"Typed at boot, answered with 0 documents" is not a regression** — it is pre-existing and unchanged.
    The readiness promise resolves when the index *opens*, not when the walk has filled it, and the search
    controller only re-runs on a *change* to the query or the toggles. So a word typed in the first second
    answers over an empty index and the list then sits stale until the next keystroke. The e2e handles it by
    retyping (`searchFor` polls). Refreshing the list when a walk finishes would be a change to APP-01-05's
    controller contract; recorded rather than smuggled in here.
